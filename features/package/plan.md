# Package

## Pattern summary

A macOS-only distribution feature: produce a signed-but-unsigned (no code-sign cert yet) `.dmg` installer for the todoz Electron app, with a custom app icon that replaces the default Electron diamond. A new dev dependency `electron-builder` consumes the existing `npm run build` output (`dist/main.js`, `dist/renderer/*`) and produces `release/todoz-<version>.dmg`. The DMG mounts to a Finder volume window with `todoz.app` and an `Applications` symlink at the top level so users drag-to-install. The app's bundle identifier is `com.theneubeck.todoz` and its display name is `todoz`. The icon source is a 1024×1024 PNG at `assets/icon.png` — created by Implement, since none exists today — and `electron-builder` converts it to a multi-resolution `.icns` at build time. The icon visual is minimal per `DESIGN.md`: a black square with rounded corners and a white checkmark inside, matching the `primary` (#000000) / `on-primary` (#ffffff) tokens. The `release/` output directory is gitignored. There is no Cucumber/Tallahassee surface here — the feature is build configuration plus a Playwright/bash verify script that exercises the produced DMG end-to-end.

**In scope:** `electron-builder` dev dependency and `package.json` `build` config block; `npm run package` script; `assets/icon.png` source asset (Implement creates it); icon-to-icns conversion at build time; bundle id `com.theneubeck.todoz`; productName `todoz`; mac/dmg target only; `release/` output gitignored; an `Applications` symlink in the DMG layout; a smoke launch test of the packaged `.app` that asserts the main window renders the brand "TODO".

**Out of scope:** code signing (requires Apple Developer ID), notarization (requires `notarytool` + cert), auto-update (would need an update server), GitHub Actions release workflow on tag (explicitly the next feature), Linux/Windows targets, custom DMG background image, custom DMG window size beyond electron-builder's defaults, App Store distribution, universal/arm64 vs intel selection (electron-builder's default for the host architecture is fine).

## Acceptance criteria

1. Given a clean working tree on macOS with `node_modules` installed, when `npm run package` is invoked, then the script exits with code 0 and `release/todoz-<version>.dmg` exists on disk.
2. Given the `.dmg` from criterion 1, when it is mounted via `hdiutil attach`, then the mounted volume contains `todoz.app` at the top level.
3. Given the mounted `todoz.app`, when its `Contents/Info.plist` is read, then `CFBundleIdentifier` equals `com.theneubeck.todoz` and `CFBundleName` equals `todoz`.
4. Given the mounted `todoz.app`, when a screenshot of its icon is captured (via `sips` extracting the icon resource, or via a Finder-style screenshot of the volume window), then the rendered icon is the custom `assets/icon.png` source — visibly distinct from the default Electron diamond.
5. Given the mounted DMG volume, when its top-level entries are listed, then `todoz.app` and `Applications` (symlink to `/Applications`) are both present at the top level.
6. Given the mounted `todoz.app`, when launched via `open <volume>/todoz.app`, then within 5 seconds Playwright connects to a window whose `[data-brand]` text equals "TODO" (smoke test that the packaged build runs).

## File map

### New files
- `assets/icon.png` — 1024×1024 PNG, RGBA, transparent background (or `surface` `#f7f9fb` background — Implement decides). Visual: a centered rounded-corner black square (radius ≈ 22% of width per Apple's macOS app icon shape grid) with a white checkmark glyph inside. Color tokens: square fill = `primary` (`#000000`), checkmark = `on-primary` (`#ffffff`). Generated by Implement using a small Node script that draws into a Canvas / SVG → PNG, or hand-crafted in any vector tool, or generated procedurally via a one-off script in `scratch/`. The committed file is the PNG only; the source script (if any) is throwaway.
- `test/data/packageConfig.spec.ts` — five unit tests over the `package.json` `build` block.
- `test/verify/package.verify.ts` — Playwright + bash verify script. Steps:
  1. Snapshot any existing `release/` artifacts so a re-run is idempotent.
  2. Spawn `npm run package` as a subprocess; assert exit code 0 (AC 1).
  3. Glob `release/todoz-*.dmg`; assert one match (AC 1 file existence).
  4. Mount the DMG via `hdiutil attach -nobrowse -readonly <dmg>`; capture the mount point (AC 2).
  5. Assert `<mount>/todoz.app` exists (AC 2).
  6. Read `<mount>/todoz.app/Contents/Info.plist` via `plutil -extract CFBundleIdentifier raw -` and assert equals `com.theneubeck.todoz` (AC 3).
  7. Read `CFBundleName` similarly; assert equals `todoz` (AC 3).
  8. Capture a screenshot of the mounted volume (Finder window or icon resource extraction via `sips -s format png <icon>`) into `test/screenshots/package-dmg-window.png` (AC 4 + AC 5 visual).
  9. List the mount root via `fs.readdirSync` and assert both `todoz.app` and `Applications` are present (AC 5 file-system).
  10. Launch the packaged app via `_electron.launch({ executablePath: '<mount>/todoz.app/Contents/MacOS/todoz' })`; wait for the first window; assert `[data-brand]` text equals "TODO" (AC 6); capture `test/screenshots/package-launched-app.png`.
  11. Detach the volume via `hdiutil detach <mount>`.
  12. Capture a baseline screenshot of `assets/icon.png` (just `cp` it into `test/screenshots/package-icon-source.png` so verify-readers can compare the rendered icon to the source).

### Files to update
- `package.json`:
  - Add `electron-builder` to `devDependencies`.
  - Add a top-level `build` block:
    ```json
    "build": {
      "appId": "com.theneubeck.todoz",
      "productName": "todoz",
      "files": ["dist/**/*", "package.json"],
      "directories": { "output": "release" },
      "mac": {
        "target": "dmg",
        "icon": "assets/icon.png",
        "category": "public.app-category.productivity"
      }
    }
    ```
  - Add a `package` script: `"package": "npm run build && electron-builder --mac dmg"`.
  - Append `&& ts-node test/verify/package.verify.ts` to the existing `verify:playwright` script.
- `.gitignore` — add `release/` so DMG artifacts are not committed.
- `package-lock.json` — updates as a side effect of `npm install electron-builder --save-dev`.

### DOM contract
No new selectors. The verify script reuses the existing `[data-brand]` selector to confirm the packaged app's main window renders the post-rename brand text "TODO".

### Visual treatment

`assets/icon.png` follows DESIGN.md tokens:
- Canvas: 1024×1024, RGBA.
- Outer shape: rounded-corner square, ~824×824 centered (≈100px margin), corner radius ~180px (≈22% of square width — Apple's macOS icon corner shape grid).
- Square fill: `primary` `#000000`.
- Glyph: white checkmark stroke inside the square. Stroke weight ~80px, white `#ffffff`. Centered, occupying ~50% of the square.
- No drop shadow, no gradient. Flat per DESIGN.md's "low-contrast outlines + tonal layers" stance.

The DMG window itself uses `electron-builder`'s default layout (no custom background image, default size). Custom background is out of scope.

## Data fixtures

None. This feature operates on build configuration and produces a transient DMG artifact at `release/todoz-<version>.dmg`. The icon source `assets/icon.png` is real source, not a fixture.

## Skill deviations (recorded in Decisions when freezing)

This plan deliberately departs from the `plan-feature` skill template in three places:

1. **No Gherkin scenarios, no `.feature` file, no step defs.** Cucumber's strengths (DOM-state assertions, fixture vault scenarios) don't apply to a build/distribution feature; forcing each AC into Given/When/Then would just describe shell commands awkwardly. AC traceability is via the verify script's per-AC assertions instead.
2. **No Tallahassee/DOM tests.** The feature changes nothing about the rendered app — only how it's packaged for distribution.
3. **No `test/fixtures/vault/todos/` fixtures.** No vault data is involved. The icon PNG is real source under `assets/`, not a fixture.

These deviations are deliberate and not problems. Implement should not add Gherkin or Tallahassee tests trying to fit the template; the unit tests in `test/data/packageConfig.spec.ts` plus the verify script in `test/verify/package.verify.ts` are the full test surface for this feature.
